## 🧭 Введение: что такое RAG и зачем он нужен в 2026 году

## БЛОК 3: ПОИСКОВЫЕ СИСТЕМЫ И RAG

### 3.1 Фундаментальное ограничение LLM и почему RAG — ответ

Языковая модель — это функция `f(токены_промпта) → токены_ответа`. Всё что она знает закодировано в весах, зафиксированных на момент обучения. Дата знаний T-lite-it-1.0 — приблизительно весна/лето 2024 года. Любой факт позже этой даты (новый пакет, изменившийся API, актуальный регламент) для модели не существует.

Fine-tuning изменяет веса модели и меняет её поведение, но не делает её достоверно осведомлённой о конкретных корпоративных фактах. Попытка «залить знания» через fine-tuning даёт модель, которая может казаться уверенной, но галлюцинирует в деталях с высокой вероятностью — известный феномен, задокументированный в нескольких академических работах 2024–2025.

Правильный способ думать о разделении задач:

```
Fine-tuning  → меняет КАК модель отвечает
               (формат, стиль, язык, поведение)
               
RAG          → даёт ЧТО модель знает прямо сейчас
               (факты, документы, актуальные данные)
```

RAG (Retrieval-Augmented Generation) решает проблему иначе: знания хранятся внешне, извлекаются при каждом запросе, подаются в контекст. Модель отвечает не «из головы», а опираясь на предоставленный документ. Задача LLM в RAG-системе трансформируется: не «вспомни факт», а «синтезируй ответ из прочитанных абзацев» — задача, с которой трансформеры справляются принципиально лучше.

RAG — enterprise use case №1 для LLM, обогнавший fine-tuning и prompt engineering как самостоятельную технику.

### Фундаментальное ограничение LLM

Языковая модель — это функция `f(токены_промпта) → токены_ответа`. Всё, что она знает, закодировано в весах, зафиксированных на момент обучения. Любой факт позже даты среза знаний — новый стандарт, обновлённый регламент, свежий инцидент — для модели не существует. Это не баг, это фундаментальное свойство архитектуры трансформеров.

Иногда инженеры пытаются залить знания через fine-tuning. Это принципиально неверное решение задачи. Исследования 2024–2025 годов (включая работы команды Anthropic) зафиксировали один и тот же паттерн: модель после fine-tuning на корпоративных данных может казаться уверенной, но галлюцинирует в деталях с высокой вероятностью — ровно там, где галлюцинации опаснее всего.

Правильное разделение задач:

```
FINE-TUNING:   меняет КАК модель отвечает
               (тон, формат, корпоративный стиль, безопасное поведение)
               → выполняется один раз, дорого, стабильно

RAG:           даёт ЧТО модель знает прямо сейчас
               (факты, документы, актуальные данные)
               → обновляется добавлением новых документов, дёшево
```

RAG — enterprise use case №1 для LLM в 2025–2026. Задача модели в RAG-системе трансформируется с «вспомни факт» на «синтезируй ответ из прочитанных абзацев». Это принципиально более надёжная задача для трансформеров.

### 3.2 Конвейер RAG: шесть компонентов и два production-слоя

Полный production RAG-конвейер состоит из шести обязательных компонентов и двух дополнительных production-слоёв:

```
ИНДЕКСАЦИЯ (offline, однократно или по расписанию):
  Документы → [Loader] → [Splitter/Chunker] → [Embedder] → [Vector Store]

ЗАПРОС (online, каждый вызов):
  Запрос → [Embedder] → [Retriever] → (опционально: [Reranker]) → [Generator/LLM]

PRODUCTION СЛОИ (параллельно):
  → [Evaluator] : faithfulness, relevance, recall
  → [Tracer]    : Langfuse / WandB Weave
```

Каждый компонент влияет на итоговое качество независимо. Распространённая ошибка: менять только генератор (заменить модель на более сильную), игнорируя качество ретривала. Если система возвращает нерелевантные чанки — даже самая мощная модель не ответит правильно.

### Анатомия полного RAG-конвейера

Наивный RAG 2023 года выглядел так:

```
Запрос → embed → top-k chunks → промпт → LLM → ответ
```

Этот пайплайн был мёртв уже в 2024-м. Он не работал в enterprise по трём системным причинам:

```
ПРОБЛЕМА 1 — Потеря контекста при чанкинге:
  Чанк: "Выручка выросла на 20%"
  → embedding не знает чей это документ — поиск промахивается

ПРОБЛЕМА 2 — Dense-поиск слепой к точным идентификаторам:
  Запрос: "ГОСТ 34.602-89"
  → семантика ищет "стандарт документации"
  → нужный чанк не в top-5

ПРОБЛЕМА 3 — Статический пайплайн не умеет рассуждать:
  База вернула мусор → LLM галлюцинирует на основе мусора
  → нет механизма проверки и самокоррекции
```

Индустриальный стандарт на июль 2026:

```
OFFLINE (индексация, однократно):
  Документы → [Парсер] → [Чанкер + Contextual enrichment] → [Embedder] → [Vector Store]

ONLINE (каждый запрос):
  Запрос → [Embedder] → [Hybrid Retriever: Dense+Sparse+RRF]
         → [Cross-Encoder Reranker] → [Generator LLM]

PRODUCTION СЛОИ (параллельно):
  → [Evaluation: RAGAS] — контроль качества
  → [Observability: LangSmith / Langfuse] — трассировка
  → [Guardrails] — безопасность
```

## 🔗 Связь с экосистемой: Fine-tuning + RAG вместе

```
FINE-TUNING (предыдущий МК):         RAG (этот МК):
  Меняет ПОВЕДЕНИЕ модели              Даёт АКТУАЛЬНЫЕ ЗНАНИЯ
  Как отвечать, когда отказать         Что именно отвечать
  Один раз, затем статично             Обновляется добавлением docs

В PRODUCTION оба вместе:
  T-lite SFT+DPO → умеет вести         База знаний Milvus →
  корпоративный диалог, отказывать     актуальная документация,
  от опасных запросов                  регламенты, тикеты

КОНКРЕТНЫЙ КЕЙС:
  Документация Astra Linux 1.8
          │ Docling
          ▼
  Markdown chunks + clean_text()
          │ contextual_chunk() + BGE-M3
          ▼
  Milvus Hybrid Search + Reranker
          │ LangGraph CRAG
          ▼
  T-lite SFT+DPO на vLLM
          │
          ▼
  "sudo astra-freeipa-install --server --setup-dns"
  ← точный ответ с источником из документации ✅
```
