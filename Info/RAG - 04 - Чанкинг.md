
### 1.2 Стратегии чанкинга: фиксированные окна и семантическое разбиение

#### Почему нельзя индексировать целый документ

Три технических ограничения:

```
ОГРАНИЧЕНИЕ 1 — Вектор документа "усредняет" темы:
  100-страничный регламент ИБ → один вектор
  Запрос "срок хранения логов" → не найдёт — тема размыта

ОГРАНИЧЕНИЕ 2 — Контекстное окно LLM ограничено:
  GPT-4o: 128k токенов ($$$)
  Локальный T-lite: 2048–8192 токенов
  100-страничный PDF: ~75 000 токенов — не влезет физически

ОГРАНИЧЕНИЕ 3 — "Lost in the middle" эффект:
  Liu et al., Stanford 2023: при контексте >10k токенов
  точность извлечения факта из середины падает с ~80% до ~30%
  Не баг — системное свойство attention-архитектуры
```

Чанкинг — не техническая деталь, это архитектурное решение, от которого зависит качество всей системы.

#### Baseline: RecursiveCharacterTextSplitter

**RecursiveCharacterTextSplitter** — производственный стандарт по умолчанию в 2026. Принцип: алгоритм пробует разбить текст по иерархии разделителей:

```
Приоритет разделителей (от наиболее к наименее значимому):
  1. "\n\n"  — границы абзацев (семантически правильные разрывы)
  2. "\n"    — переносы строк
  3. ". "    — конец предложения
  4. " "     — пробел (слова)
  5. ""      — крайний случай, побуквенно (никогда не хочется)
```

Алгоритм режет только когда чанк превысил `chunk_size`, используя максимально осмысленный разделитель. Границы получаются более семантичными, чем простой «срез по n символов».

**Данные бенчмарков (2026):**
- Fastio/FloTorch February 2026 (50 академических статей): recursive 512-token = 69% accuracy — **первое место среди 7 стратегий**
- Chroma Research: 85–89% recall при 400–512 токенах
- «Контекстный обрыв» (context cliff) ~2500 токенов: выше этого значения quality деградирует

```
ПРАВИЛО:
  chunk_size    = 512 токенов   (рабочий диапазон 400–1024)
  chunk_overlap = 128 токенов   (10–25% от chunk_size)
  separators    = ["\n\n", "\n", ". ", " ", ""]
```

**Почему overlap важен:** ключевая мысль может оказаться точно на границе чанков — overlap гарантирует, что она войдёт хотя бы в один из них. Microsoft Azure рекомендует 25% если recall низкий; сверх 25% растут хранилище и стоимость эмбеддингов без значимого прироста.

#### ✏️ Код: базовая нарезка

```python
from langchain_text_splitters import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=512,
    chunk_overlap=128,
    separators=["\n\n", "\n", ". ", " ", ""],
)

chunks = splitter.split_text(doc_text)
print(f"Документ: {len(doc_text)} символов → {len(chunks)} чанков")
# Средний размер чанка: ~400-500 токенов (512 - немного overlap'а с предыдущим)
```

#### Семантический чанкинг: когда стоит платить больше

Семантический чанкинг определяет границы по смысловому разрыву — через popарное измерение cosine similarity эмбеддингов соседних предложений.

```
ПРИНЦИП РАБОТЫ:
  1. Разбить документ на предложения
  2. Embed каждое предложение
  3. Для каждой пары (предл_i, предл_{i+1}) вычислить cosine_sim
  4. Найти «провалы» (резкое падение similarity)
  5. Провалы = границы смысловых блоков → чанки
```

**Реальные данные 2025–2026 неоднозначны:**

- Chroma Research: semantic chunking — 91.9% recall vs 85–89% у recursive. Разница: 2–9 п.п.
- NAACL 2025 paper (Vectara): «вычислительные затраты не оправданы стабильным приростом качества»
- Vecta benchmark February 2026 (50 academic papers): recursive 69%, semantic 54% — **semantic проиграл**
- MDPI Bioengineering November 2025 (клинические документы): adaptive chunking 87% vs fixed 13%

**Вывод:** semantic chunking выигрывает на структурированных корпусах (официальные документы, стандарты). Проигрывает на академических текстах. Правило SRE: начинай с recursive. Добавляй semantic только после RAGAS-eval.

#### Contextual Chunking (Anthropic, 2024): главный прирост за 1 LLM-вызов

Не отдельная стратегия разбиения — это обогащение, накладываемое поверх любой стратегии. По данным Anthropic: **-67% промахов retrieval** при комбинации с reranker.

```
ЧАНК БЕЗ КОНТЕКСТА:
  "Выручка выросла на 20%"
  → embedding не знает: чья выручка? когда? в каком документе?
  → запрос "Ромашка выручка 2025" → ПРОМАХ

ЧАНК С CONTEXTUAL PREFIX:
  "[Контекст: Годовой отчёт ООО Ромашка 2025. Финансовые показатели.]
   Выручка выросла на 20%"
  → запрос "Ромашка выручка 2025" → ПОПАДАНИЕ ✅
```

**Алгоритм:**

```
ШАГ 1: Один вызов быстрой LLM
        Prompt: "Опиши документ в 2 предложениях. Начни с темы и источника."
        Input:  первые 2000-3000 символов документа
        Output: summary (~50-100 токенов)

ШАГ 2: Стандартная нарезка (recursive или semantic)
        Получаем N чанков

ШАГ 3: К каждому чанку приклеиваем prefix:
        enriched = f"[Контекст: {summary}]\n\n{chunk}"
```

**Стоимость:** 1 LLM-вызов на документ (не на чанк!). При 100 документах — 100 вызовов. Дёшево. Если документ обновляется редко — кешируй summary.

#### ✏️ Код: Contextual Chunking

```python
from langchain_text_splitters import RecursiveCharacterTextSplitter
from langchain_openai import ChatOpenAI

def contextual_chunk(doc_name: str, doc_text: str, llm) -> list[dict]:
    """
    Contextual Chunking (Anthropic, 2024):
    К каждому чанку приклеиваем summary документа.
    Результат: -67% промахов retrieval (данные Anthropic).
    Стоимость: один LLM-вызов на документ.
    """
    # Шаг 1: summary — просим описать документ в 2 предложениях
    # Начало документа (первые 3000 символов) содержит тему и контекст
    summary_prompt = f"""Опиши документ в 2 коротких предложениях.
Начни с названия или темы документа.
Документ (начало): {doc_text[:3000]}"""

    summary = llm.invoke(summary_prompt).content.strip()

    # Шаг 2: стандартная нарезка
    splitter = RecursiveCharacterTextSplitter(
        chunk_size=512, chunk_overlap=128
    )
    raw_chunks = splitter.split_text(doc_text)

    # Шаг 3: обогащение — prefix с summary к каждому чанку
    enriched = []
    for i, chunk in enumerate(raw_chunks):
        enriched.append({
            "text":     f"[Контекст: {summary}]\n\n{chunk}",
            "source":   doc_name,
            "chunk_id": i,
        })

    return enriched
```

**Использование в pipeline:**

```python
all_chunks = []
for doc_name, doc_text in parsed_docs.items():
    print(f"Обрабатываем: {doc_name}")
    chunks = contextual_chunk(doc_name, doc_text, llm_fast)
    all_chunks.extend(chunks)

# Сохраняем для переиспользования (парсинг + LLM-вызов стоят дорого)
import json
with open('/workspace/chunks.json', 'w', encoding='utf-8') as f:
    json.dump(all_chunks, f, ensure_ascii=False, indent=2)
```

#### Parent-Child чанкинг: маленькие индексируем, большие возвращаем

Поиск лучше работает на маленьких чанках (100–200 токенов — точный semantic match), а LLM лучше работает с большим контекстом (512–1024 токена). Решение:

```
STORE:
  vector_store: child_chunks (~100-200 токенов) — для точного поиска
  doc_store:    parent_chunks (~512-1024 токена) — для богатого контекста
  link:         child_id → parent_id

QUERY:
  1. Поиск по child_chunks → top-20 child_ids
  2. Resolve parent_ids → top-N parent_chunks
  3. Deduplicate parents → передаём в LLM
```

В LangChain это реализует `ParentDocumentRetriever`. В practice: хранит child в vectorstore, parent в `InMemoryDocumentStore`.

По данным ARAGOG benchmark (2024): **Sentence Window Retrieval — метод №1 по retrieval precision** среди всех протестированных подходов. Индексируем отдельные предложения (~50-100 токенов), при попадании возвращаем окно ±2-3 предложения вокруг найденного.

#### Чанкинг кода: отдельный кейс

Для корпоративных кодовых баз (Python-скрипты, Terraform, Kubernetes manifests) обычный recursive splitter режет по предложениям, что нарушает семантику. Правильно — резать по синтаксическому дереву (AST):

```
CodeSplitter (LlamaIndex / LangChain):
  - парсит AST через tree-sitter (40+ языков)
  - границы чанков = границы функций, классов, методов
  - metadata: file_path, function_name, line_start, line_end
```

### 3.3 Чанкинг: разбивка документов на фрагменты

Чанк — минимальная единица хранения в векторной базе. Каждый чанк получает свой вектор и независимо участвует в поиске.

**Почему нельзя индексировать целый документ:**
- Вектор целого документа усредняет все его темы → плохая точность поиска
- Контекстное окно LLM ограничено → нельзя передать 100-страничный документ целиком
- Разные части документа отвечают на разные вопросы

Передача 100-страничного документа целиком в каждый промпт — это огромная переплата за токены, кратный рост latency и риск эффекта «lost in the middle» (когда модель игнорирует факты из середины текста).

**Параметры чанкинга и их влияние:**

`chunk_size` — целевое количество символов (или токенов) в чанке. Стандарт в 2026: 400-800 токенов. Слишком маленький → потеря контекста (предложение без абзаца неоднозначно). Слишком большой → один чанк охватывает несколько тем → плохая точность эмбеддинга.

`chunk_overlap` — количество символов, копируемых из конца предыдущего чанка в начало следующего. Цель: предотвратить ситуацию, когда ключевая мысль оказывается "разрезана" на границе. Стандарт: 10-15% от chunk_size.

`separators` — иерархия разделителей для `RecursiveCharacterTextSplitter`. Сначала пробует разбить по `\n\n` (абзацы), если чанк всё равно длинный — по `\n`, затем по пробелу, в крайнем случае по символу. Это семантически грамотнее, чем просто резать по длине.

**Parent-Child чанкинг** — техника (2025): в векторной базе хранятся маленькие "дочерние" чанки (~100 токенов) для высокой точности поиска, но при попадании извлекается "родительский" чанк (вся страница). Модель получает богатый контекст при высокой точности поиска.

**Семантический чанкинг** — исследование Databricks (2025) показало улучшение recall на 9% по сравнению с fixed-size подходом. Суть: граница чанка определяется не длиной, а семантическим разрывом (измеряемым через эмбеддинги соседних предложений).
