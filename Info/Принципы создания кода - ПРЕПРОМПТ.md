1. Фиксируй требования и ограничения.  
   — Заранее задай ОС, путь, Docker, порт, volume, версии, ожидаемые файлы.

2. Декомпозируй задачу на мелкие шаги.  
   — Не «весь проект», а Dockerfile → compose → Jupyter → API → HTML → очистка.

3. Сначала план, потом код.  
   — AI перечисляет файлы, зависимости, команды и риски до реализации.

4. Задай критерии SMART готовности.  
   — Например: raw.html в volume, TXT с маркерами, localhost:8888 работает.

5. Фиксируй версии зависимостей.  
   — requirements.txt с точными версиями, а не «поставь всё».

6. Пиши тесты вместе с кодом.  
   — Проверяй HTTP-ошибки, timeout, невалидный URL, пустой HTML.

7. Не доверяй внешним полученным объектам.  
   — Не исполняй, не передавай в shell, ограничивай размер.

8. Секреты — храни и обрабатывай согласно концепциям безопасности.  
   — API-ключи в .env/переменных, не в notebook и Git.

9. Логируй и показывай понятные ошибки.  
   — URL, HTTP-код, размер, время, путь файла; пользователю — кратко.

10. Проверяй результат авто и вручную.  
    — Линт, тесты, diff, повторный запуск на разных URL.

11. KISS: Keep It Simple простое решение.  
    — Сначала requests + BeautifulSoup; Playwright только при необходимости.

12. DRY: Don’t Repeat Yourself не дублируй логику.  
    — Повторяющееся выноси в функцию, но без фанатичной абстракции.

13. YAGNI: You Aren’t Gonna Need It не добавляй лишнее.  
    — Никаких БД, очередей, авторизации и лишних форматов «на будущее».

14. SOLID: 
    — fetch_html, save_html, clean_html, save_text, notebook — раздельно.

* S — Single Responsibility Principle (Принцип единственной ответственности): Один класс должен решать только одну задачу.
* O — Open/Closed Principle (Принцип открытости / закрытости): Код должен быть открыт для расширения, но закрыт для изменения.
* L — Liskov Substitution Principle (Принцип подстановки Барбары Лисков): Наследники должны легко заменять своих родителей, ничего не ломая.
* I — Interface Segregation Principle (Принцип разделения интерфейса): Лучше много специализированных интерфейсов, чем один универсальный.
* D — Dependency Inversion Principle (Принцип инверсии зависимостей): Код должен зависеть от абстракций, а не от конкретных деталей.

14. Разделяй изменения по слоям: fetch, clean, save, UI.  
    — Не смешивай URL, HTTP, HTML, файлы и ошибки в одной функции.

15. Fail Fast: явные ошибки.  
    — Проверяй URL, timeout, статус, content-type, размер, наличие файла.

16. Отделяй данные от конфигурации.  
    — Секреты в env, несекретные настройки в config.py, локальное в .gitignore.

17. Покрывай тестами поведение.  
    — Мокай сеть; проверяй 404/500, timeout, пустой HTML, удаление тегов.

18. Рефактори маленькими шагами.  
    — Тесты → одно изменение → тесты/линтер → diff → дальше.

19. Код должен быть читаемым и проверяемым, с type hints и README.  
    — Понятные имена, мелкие функции, docstring, стиль, примеры запуска.
